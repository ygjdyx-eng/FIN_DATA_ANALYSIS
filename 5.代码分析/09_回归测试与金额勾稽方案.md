# 回归测试与金额勾稽方案

## 1. 目标与边界

- 【代码事实】本方案覆盖 34 个过程、四个阶段、PLIS/AGS/GLIS 三条分支及最终物理结零删除。
- 【代码事实】当前仅完成静态分析，尚未连接 Oracle 或执行任何 SQL；下列 SQL 必须先在只读副本/测试库按实际 DDL 校正。
- 【合理推断】测试重点不是只验证“过程成功”，而是证明行数、金额、账龄档、结零候选、实际删除范围和同月重跑均符合书面口径。

## 2. 测试前置物

1. 【待业务确认】测试 schema、Oracle 版本、`NLS_DATE_FORMAT/NLS_NUMERIC_CHARACTERS`。
2. 【待业务确认】62 个活动表/视图式对象的 DDL、索引、触发器、同义词，以及34个唯一序列的定义。
3. 【待业务确认】`SUBJECTENUMERATIONAGING`、`TEMP_AGING_COMBIN` 的测试配置快照。
4. 【待业务确认】至少一个已关账月份的脱敏源数据、总账控制数、当前报表正确结果。
5. 【待业务确认】单币种或多币种规则、金额精度/容差、各分支零余额业务主键。
6. 【合理推断】测试库应从可恢复快照开始；阶段4前另做最终表备份，并禁止与其他测试会话并发。

## 5. 账龄边界预期

对 PLIS/GLIS 使用与代码一致的表达式生成期望档：

```sql
SELECT default_effective_date,
       MONTHS_BETWEEN(:month_end, default_effective_date) AS month_diff,
       CASE
         WHEN MONTHS_BETWEEN(:month_end, default_effective_date) < 3  THEN 1
         WHEN MONTHS_BETWEEN(:month_end, default_effective_date) < 12 THEN 2
         WHEN MONTHS_BETWEEN(:month_end, default_effective_date) < 36 THEN 3
         WHEN MONTHS_BETWEEN(:month_end, default_effective_date) < 60 THEN 4
         ELSE 5
       END AS expected_bucket
FROM test_dates;
```

- 【代码事实】正好 3/12/36/60 个月分别进入档2/3/4/5。
- 【合理推断】测试应分别设置两端均为月末和日号不一致两组，避免只覆盖整数月份。
- 【合理推断】在修复 R-009 后，将 `:month_end` 绑定为 DATE，并在至少两种 NLS_DATE_FORMAT 下得到相同结果。

## 6. 阶段勾稽点

### 6.1 阶段1：源事实 → 月度桥接表

每个分支至少记录：源过滤行数、目标行数、源金额、目标金额、科目/机构/NULL字段分布。

```sql
SELECT je_source,
       COUNT(*) AS row_count,
       SUM(amount) AS amount_sum,
       COUNT(DISTINCT policy_no) AS policy_count
FROM temp_month_personal_insurance01
GROUP BY je_source;
```

- 【合理推断】目标金额应与“完全复刻阶段1 WHERE 和金额表达式”的源控制查询一致。
- 【代码事实】PLIS 13 分支还应检查同一源行是否落入多个机构范围，尤其 `100001` 与 `AAA`。
- 【代码事实】统计阶段2将读取但阶段1未显式写字段的 NULL 率，例如 `PERIOD_NAME/SHORT_NAME/PRODUCT_NO/SEGMENT6`。

### 6.2 阶段2：月度桥接 → 历史 → 当批

每个 PLIS 分支记录以下状态：

```sql
SELECT aging_marker,
       zero_closing_marker,
       COUNT(*) AS row_count,
       SUM(amount) AS amount_sum
FROM temp_finance_aging_analysisplis01
GROUP BY aging_marker, zero_closing_marker
ORDER BY aging_marker, zero_closing_marker;
```

```sql
SELECT aging_month,
       zero_closing_marker,
       COUNT(*) AS row_count,
       SUM(amount) AS amount_sum
FROM temp_finally_finance_aging_analysis01
GROUP BY aging_month, zero_closing_marker
ORDER BY aging_month, zero_closing_marker;
```

验收关系：

- 【合理推断】历史新增标记0金额应等于阶段1中通过阶段2细粒度 `HAVING SUM<>0` 的明细金额。
- 【代码事实】标记2金额按各“科目+保单+截止日期”组应精确为0；标记1按配置账龄组合及“地区+科目+保单”应精确为0。
- 【合理推断】当批标记0金额应能按业务键回溯至历史标记0；任何差异需解释为非零分组粒度变化。
- 【代码事实】AGS单独检查 `2202010206` 全历史删除前后；GLIS检查两轮标记2和被排除科目。

### 6.3 阶段3：当批 → 最终表

```sql
SELECT je_source,
       aging_period,
       COUNT(*) AS row_count,
       SUM(amount) AS amount_sum
FROM finance_aging_analysis
WHERE aging_period = :aging_period
GROUP BY je_source, aging_period
ORDER BY je_source;
```

- 【合理推断】按各阶段3 GROUP BY 粒度重算，当批 `SUM(amount)` 应与最终新增金额一致。
- 【代码事实】PLIS需分别勾稽13张表；GLIS需分别勾稽三类科目；AGS需先验证资格组再验证细粒度汇总。
- 【合理推断】同时记录 `MIN/MAX(DEFAULT_EFFECTIVE_DATE)`、NULL保单/账户/机构数量和业务场景多值组，验证 MIN/MAX 规则没有意外压缩。

### 6.4 阶段4：候选 → 删除 → 保留

阶段4前后记录：

```sql
SELECT je_source,
       COUNT(*) AS row_count,
       SUM(amount) AS amount_sum
FROM finance_aging_analysis
WHERE aging_period = :aging_period
GROUP BY je_source;
```

- 【合理推断】对正式零余额键，删除行金额应为0；删除前金额=删除后金额+删除金额。
- 【合理推断】若允许精确零删除，则最终来源总金额理论上不变；若变化非0，必须阻断上线。
- 【代码事实】候选表行数不等于删除行数；必须按实际 EXISTS 键预演删除集合。

## 7. 三个高风险只读预演

### 7.1 R-001：PLIS遗漏科目键的额外删除行

```sql
WITH zero_keys AS (
  SELECT policy_no, branch_code, subject_id
  FROM finance_aging_analysis
  WHERE aging_period = :aging_period
    AND je_source = 'PLIS'
  GROUP BY policy_no, branch_code, subject_id
  HAVING SUM(amount) = 0
), buggy_delete_set AS (
  SELECT c.*
  FROM finance_aging_analysis c
  WHERE c.aging_period = :aging_period
    AND c.je_source = 'PLIS'
    AND EXISTS (
      SELECT 1 FROM zero_keys z
      WHERE z.policy_no = c.policy_no
        AND z.branch_code = c.branch_code
    )
), correct_delete_set AS (
  SELECT c.*
  FROM finance_aging_analysis c
  WHERE c.aging_period = :aging_period
    AND c.je_source = 'PLIS'
    AND EXISTS (
      SELECT 1 FROM zero_keys z
      WHERE z.policy_no = c.policy_no
        AND z.branch_code = c.branch_code
        AND z.subject_id = c.subject_id
    )
)
SELECT 'BUGGY' AS set_name, COUNT(*) AS rows_, SUM(amount) AS amount_ FROM buggy_delete_set
UNION ALL
SELECT 'CORRECT', COUNT(*), SUM(amount) FROM correct_delete_set;
```

- 【合理推断】两集合行数/金额的差就是遗漏科目条件带来的扩大范围；上线门禁为差集 0，或业务书面批准更宽删除。

### 7.2 R-002：AGS NULL保单候选

```sql
SELECT period_name, subject_id, je_source, agent_name,
       aging_period, business_scene_no,
       COUNT(*) AS row_count, SUM(amount) AS amount_sum
FROM finance_aging_analysis
WHERE je_source = 'AGS'
  AND aging_period = :aging_period
  AND policy_no IS NULL
GROUP BY period_name, subject_id, je_source, agent_name,
         aging_period, business_scene_no
HAVING SUM(amount) = 0;
```

- 【代码事实】该查询返回的组按现代码会在候选中写保单 `'000'`，但不能与源 NULL 通过 `'null'` 占位匹配。

### 7.3 R-015：GLIS 1301候选扩删其他账户

```sql
WITH zero_1301 AS (
  SELECT policy_no, subject_id, je_source, aging_period, business_scene_no
  FROM finance_aging_analysis
  WHERE je_source = 'GLIS'
    AND aging_period = :aging_period
    AND subject_id = '2243010106'
    AND account_segment = '1301'
  GROUP BY policy_no, subject_id, je_source, aging_period, business_scene_no
  HAVING SUM(amount) = 0
)
SELECT c.account_segment,
       COUNT(*) AS rows_,
       SUM(c.amount) AS amount_
FROM finance_aging_analysis c
WHERE c.je_source = 'GLIS'
  AND c.aging_period = :aging_period
  AND EXISTS (
    SELECT 1 FROM zero_1301 z
    WHERE z.subject_id = c.subject_id
      AND z.je_source = c.je_source
      AND z.policy_no = c.policy_no
      AND (z.business_scene_no = c.business_scene_no
           OR z.business_scene_no IS NULL AND c.business_scene_no IS NULL)
  )
GROUP BY c.account_segment
ORDER BY c.account_segment;
```

- 【合理推断】任何非1301账户行都是现有 DELETE 会一并命中的范围；是否合理需业务确认。

## 8. 重跑、故障与并发

| 用例 | 操作 | 预期/门禁 |
|---|---|---|
| I-01 同月重跑 | 完整链路执行两次 | 【待业务确认】若目标为覆盖，第二次最终行数/金额必须与第一次一致；现代码预计不满足 |
| I-02 阶段2重跑 | 只重复一个 PLISNN02 | 历史 `AGING_MARKER` 不应重复；现代码需先证明或修复 |
| I-03 阶段3重跑 | 只重复一个汇总过程 | 最终同来源期间不重复；现代码需先证明或修复 |
| I-04 阶段1故障 | 第一次TRUNCATE后注入错误 | 记录实际残留和恢复步骤，证明可从快照/检查点恢复 |
| I-05 循环中故障 | PLIS日期/组合循环中注入错误 | 已提交标记必须可识别和补偿 |
| I-06 GLIS汇总故障 | 第一段COMMIT后注入错误 | 不得把仅第一类科目完成当作整过程成功 |
| I-07 并发阶段1 | 两会话交错AGS/GLIS | 调度互斥应阻止第二会话；否则测试应暴露共享表被清空 |
| I-08 并发阶段4 | 两期间同时执行 | 调度互斥应阻止候选表互相覆盖 |

## 10. 通过标准

1. 34 个过程均编译有效，调用链在测试库完整成功且日志能闭环。
2. 三种已确认参数格式分别只用于对应阶段，边界/非法值行为明确。
3. 每阶段行数、金额和关键NULL分布均有基线；差异可以追溯到明确规则。
4. R-001 扩大删除差集为0或已修复；R-002 NULL保单可正确匹配；R-015 删除范围经业务批准。
5. 所有删除组按正式业务主键金额为0，删除前后来源总金额勾稽一致。
6. 3/12/36/60 月边界、未来日期、月末小数月全部符合书面口径。
7. 同期间重跑结果满足选定语义；失败恢复和并发互斥测试通过。
8. 单币种保证或币种维度已形成可验证约束，不再依赖口头假设。
